# React issue-writing evidence

Maintenance record for [the issue workflow](issues.md) and [React issue profile](profiles/react-issues.md). Ordinary drafting does not require this report. The observations below concern writing and triage information, not verified React behavior.

## Coverage and method

The study covers issues created from October 19, 2023 through October 19, 2026, using a GitHub API snapshot retrieved on October 19, 2026. The final day is partial. The earliest returned creation timestamp is `2023-10-19T10:43:23Z`; the latest is `2026-10-19T06:20:33Z`. Implementation and evaluation were completed on October 20, 2026.

Inventory query: `repo:react/react is:issue created:START..END`, sorted by creation time ascending, 100 results per page. Each interval below stayed below GitHub Search's 1,000-result limit. All pages were retrieved; each response reported complete results, and unique issue counts matched the reported totals. PRs were excluded explicitly. These are snapshot counts, not a continuously updated census.

For close reading, select eight issues per interval: one open and one closed from each of four heuristic buckets. Classify titles and labels in this order: feature-request/proposal/RFC/enhancement terms, compiler, DevTools, then core/other. Within each bucket and state, select the middle issue by creation time and number from reports with at least one comment and 50–900 whitespace-delimited body words. All 24 selections had the requested state. Read their bodies and inspect the discussions, with particular attention to clarification, corrections, and closure. The 24 comment endpoints returned 149 comments; short acknowledgments, bot reminders, and repeated quotations were not treated as writing evidence.

Reserve six different issues before reading their bodies: the middle remaining issue by number in core/other and request buckets for periods one and three, and compiler and DevTools for period two, using the same body-length limits. These were used only for the drafting checks below. The [source manifest](source-manifest.md#react-issue-history) registers every selected issue and the pinned templates.

## Observations and editorial decisions

- **A trigger distinguishes a report from an error dump.** [#29902](https://github.com/react/react/issues/29902) identifies the legacy transform, development mode, and false conditional. [#28787](https://github.com/react/react/issues/28787) distinguishes embedded DevTools from the browser extension. Recommendation: preserve setup, action, observation point, and relevant environment rather than imposing a universal environment checklist.
- **A reproduction link does not prove the described scenario.** In [#36128](https://github.com/react/react/issues/36128#issuecomment-4111603685), a contributor asks for a Playground reproduction; later discussion distinguishes different function forms. [#32964](https://github.com/react/react/issues/32964) supplies localhost, while [#36937](https://github.com/react/react/issues/36937) supplies an internal site and copied error-report text. Recommendation: identify missing shareable material without inventing it or blocking a useful draft.
- **Diagnosis changes after the opening report.** [#29202](https://github.com/react/react/issues/29202#issuecomment-2125254185) identifies a nondefault compiler setting during discussion. [#33181](https://github.com/react/react/issues/33181#issuecomment-2874630729) evolves from a crash report into a detection request. Recommendation: separate observations, hypotheses, and later conclusions; an issue's current title and body need not represent its original framing.
- **Closure is not a quality or correctness label.** [#28817](https://github.com/react/react/issues/28817#issuecomment-2233037115) closes after inactivity. [#28323](https://github.com/react/react/issues/28323#issuecomment-2018010191) closes after the problem stops reproducing; [#33031](https://github.com/react/react/issues/33031#issuecomment-3141085472) closes with the existing tradeoff retained. Recommendation: state the actual conclusion when known, never infer a shipped fix from state alone.
- **Feature requests benefit from the task and limitation.** [#32961](https://github.com/react/react/issues/32961) explains placement into DOM controlled by another application despite using bug headings. [#29757](https://github.com/react/react/issues/29757) offers several possible APIs for a ref-composition need. Recommendation: lead with the use case and desired outcome; API design, alternatives, and reproduction steps are conditional, not mandatory proposal sections.
- **Length and confidence do not establish evidence.** [#35395](https://github.com/react/react/issues/35395) supplies measurements but no public reproduction; its discussion adds context about timing attribution. [#37078](https://github.com/react/react/issues/37078) provides detailed reported experiments without an attached standalone reproduction. [#35678](https://github.com/react/react/issues/35678#issuecomment-3840269458) receives a correction that the reported package is unrelated. Recommendation: preserve useful observations and their provenance, and avoid strengthening unverified causes or scope.

The runtime, compiler, and DevTools forms directly support distinct fields and destinations. Preserving automated DevTools values is a form instruction. Proportionate length, symptom-oriented titles, and a lightweight feature-request path are editorial recommendations, not measured predictors of maintainer response or universal React policy.

## Reserved-case checks

These are manual, same-session drafting and review checks against the six reserved bodies, not an independent model benchmark or a before/after quality score. No reproduction code or linked application was run. The short outputs below record the checked behavior without republishing the source bodies.

1. **[#28884](https://github.com/react/react/issues/28884), runtime body rewrite:** retain the runtime headings and reported `^18.0.0` range. Separate the observed property mutation from the reporter's sealing expectation, and flag the contradictory sealing sentence. Checked: no claim that the range is an exact installed version or that the expectation is a verified guarantee.
2. **[#28866](https://github.com/react/react/issues/28866), feature-request condensation:** “Consider a named wrapper for effects with an empty dependency array to make their intent clearer to new React developers.” Keep `useOnLoadEffect` as the proposed name, not an existing API. Checked: no promise that effects run exactly once and no invented bug-reproduction section.
3. **[#33057](https://github.com/react/react/issues/33057), title only for the React compiler form:** “[Compiler Bug]: Table controls stop responding with React Compiler enabled.” Checked: retains the applicable form prefix, narrows the broad original claim to supplied symptoms, returns no body, and does not claim independent reproduction.
4. **[#32642](https://github.com/react/react/issues/32642), DevTools prose review:** “The report includes an error and version, but the local URL is not accessible to maintainers and the steps contain only an image. Provide the interaction sequence and a shareable reproduction.” Checked: leaves automated fields intact and does not infer screenshot contents or actions.
5. **[#36419](https://github.com/react/react/issues/36419), request reframing:** “Consider using native browser events in place of synthetic events. The report needs a concrete affected interaction to substantiate its interoperability concern.” Checked: treats the proposed change as a request, avoids endorsing the unsupported all-versions accusation, and identifies the evidence gap.
6. **[#35903](https://github.com/react/react/issues/35903), compiler body rewrite:** describe the supplied generated output as recreating the formatter when `date` changes; retain the reported `useMemo` comparison. Checked: the Playground versions remain unspecified, no benchmark is invented, and protected code such as `datetime` is not silently repaired.

Additional routing checks used synthetic inputs: a Chinese note saying an application spinner persists after a failed request produced “The loading indicator remains visible after the request fails,” with steps and versions marked as missing; the application using React did not activate the React tracker profile. A non-React template with “Problem” and “Desired outcome” retained those headings for a feature request. Ordinary README and PR requests continued to route to their existing references rather than issue guidance. These checks assess instruction consistency, not runtime correctness or general model reliability.

Review follow-up: a request to add CSV export to a tool that already exports JSON was checked as a workflow improvement, without claiming export was impossible or inventing an affected audience. A title-only React runtime report with supplied symptoms but no version or reproduction was checked for a `Bug: ` prefix and title-only output, without a body-field or latest-release checklist. These manual edge-case checks cover the narrowed feature-request wording and bug-body profile scope; automated reference tests do not evaluate these prose decisions.

## Limitations

Selection favors medium-length reports with discussion, excludes many very short and very long reports, and does not statistically represent writing quality. Labels and titles overlap: the request bucket contains performance and compiler reports, while core/other includes documentation, support, and unrelated reports. They are sampling aids, not reliable issue-type classifiers. Forms, bodies, titles, labels, and comments may have changed since creation; edit histories were not reconstructed. Comments were retrieved separately from the inventory, so the snapshot is not atomic. Reaction counts, closure, and author association were not used as proof of correctness.

Coverage is concentrated on runtime, compiler, DevTools, and requests. It does not establish separate conventions for build/CI, tests, React Native, accessibility, or security reporting. No causal claim is made that a format gets issues fixed. All selected API records were accessible; linked repro applications, images, external documents, and their availability were not independently verified. Publish only this synthesis and provenance metadata, not a raw issue corpus. Recheck the destination's current template when drafting a real issue.
